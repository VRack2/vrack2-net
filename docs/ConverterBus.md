# ConverterBus — устройство TCP-провайдера

**ConverterBus** применяется, когда требуется организовать связь с оборудованием, подключённым через преобразователи интерфейсов типа **Ethernet ↔ Serial / RS485 / CAN**.

Примеры устройств, работающих с **ConverterBus**, можно найти в следующих репозиториях:

- [vrack2-modbus](https://github.com/VRack2/vrack2-modbus) — набор устройств для упрощённой работы с Modbus RTU-устройствами;  
- [vrack2-other-rtu](https://github.com/VRack2/vrack2-other-rtu) — набор устройств для работы с различными специфическими Modbus RTU-устройствами.

**Важно:** ConverterBus — это не просто «устройство-труба» к преобразователю. Это сложная система, отвечающая за управление соединениями, флагами, очередями и другими аспектами взаимодействия. Благодаря этому разработчики и пользователи получают максимально гибкие возможности для опроса реальных устройств.

---

## Организация связи

Предположим, у вас есть три Modbus RTU-устройства, подключённых к одному преобразователю **Ethernet ↔ RS485**, и вы хотите управлять ими с помощью VRack2.

Для этого необходимо добавить устройство **ConverterBus** и настроить параметры подключения. Пример конфигурации в сервис-файле:

> **⚠️ Не забывайте:** в VRack2 Manager доступна встроенная документация по всем параметрам.

```json
{
  "id": "Provider",
  "type": "vrack2-net.ConverterClient",
  "options": {
    "devices": 3,
    "socket": {
      "host": "192.168.1.200",
      "port": 4001
    },
    "debug": true
  }
}
```

Особенность таких сетей (например, RS485) заключается в том, что одновременно можно общаться только с **одним** устройством в шине. Однако протоколы (например, Modbus RTU) обычно поддерживают адресацию: вы выбираете целевое устройство по его уникальному адресу.

Чтобы избежать конфликтов и обеспечить корректный обмен, каждое виртуальное устройство в VRack2 должно обращаться к шине **по очереди**.

Рассмотрим пример.

Пусть у вас есть три VRack2-устройства, представляющих три физических Modbus-устройства, подключённых к одному Ethernet↔RS485-преобразователю:

- `Device1`  
- `Device2`  
- `Device3`

Каждое из них должно:

1. Получить **экземпляр провайдера** (через вход `bus`), чтобы выполнять запросы;  
2. Выполнить необходимые операции;  
3. Передать управление обратно в `ConverterBus`.

Обычно такие устройства имеют вход возвращаемый порт `bus`.

Типичная реализация внутри устройства может выглядеть так:

```ts
/**
 * Обработчик входа `bus`.
 * При получении провайдера устройство получает управление.
 * Это основная точка входа для взаимодействия с оборудованием.
 */
async inputBus(provider: TCPProvider) {
  // Сохраняем ссылку на провайдер
  this.Provider = provider;

  // Проверяем, можно ли выполнять запрос.
  // Если нет — метод canRequest() выбросит исключение (его не нужно перехватывать).
  this.Provider.canRequest();

  // Выполняем необходимые операции (например, чтение регистров).
  // При возникновении ошибки её перехватит ConverterBus.
  // При желании вы можете обрабатывать ошибки самостоятельно и пробрасывать их выше.
  await this.update();
}
```

Как только метод `inputBus` завершает выполнение, считается, что устройство **освободило** провайдер и передало управление обратно в `ConverterBus`.

Представьте, что внутри `ConverterBus` работает примерно следующий цикл:

```ts
for (const device of devices) {
  try {
    // Последовательно передаём провайдер каждому устройству
    await this.ports.output[device].push(this.Provider);
  } catch (err) {
    // Обработка ошибок отдельного устройства
    this.error('Error in device', err);
  }
}
```

**Важно:** внутри `ConverterBus` предусмотрена защита от забытого `await`. Если устройство не вернёт управление в течение ~10 секунд, соединение будет принудительно разорвано, и сгенерируется `alert` с диагностической информацией.

## Типы построения схем опроса

Чтобы опрос заработал корректно, необходимо соблюсти следующие условия:

- Вход `bus` у устройства должен быть подключён к одному из выходов `dev%d` у `ConverterBus`.  
  **❗ Важно:** один выход `ConverterBus` (`dev1`, `dev2` и т.д.) можно подключать **только к одному** устройству.
- Параметры сокета (`host`, `port`) в `ConverterBus` должны быть указаны корректно — чтобы он мог установить соединение с преобразователем интерфейсов.  
- Каждое устройство должно корректно обрабатывать вход `bus` (например, как в примере `inputBus` выше).

Пример корректного сервис-файла:

```json

      "type": "vrack2-net.ConverterBus",

        "socket": {
          "host": "172.16.103.118",

        "debug": false,
        "devices": 3
      },

        "Provider1.dev1 -> Dev::Control1.bus",
```

## Работа с классом провайдера

Как уже упоминалось, для работы с RTU-устройствами рекомендуется использовать готовые наборы:

- [vrack2-modbus](https://github.com/VRack2/vrack2-modbus) — для упрощённой работы с Modbus RTU;  
- [vrack2-other-rtu](https://github.com/VRack2/vrack2-other-rtu) — для специфичных устройств на базе Modbus RTU.

В сетях типа RS485 обмен данными происходит по следующему сценарию:

1. Отправляем запрос в шину.  
2. Ожидаем ответ в течение заданного `timeout`.  
3. Если данные пришли — проверяем, является ли это **полный ответ нашего устройства**:  
   - Если структура и длина соответствуют ожидаемой — считаем, что пакет получен полностью, и обрабатываем его.  
   - Если данные неполные или повреждены — продолжаем ожидание до истечения `timeout`.  
4. Если ничего не пришло — считаем, что устройство недоступно («offline»).

Для определения, **получен ли полный пакет**, необходимо задать собственную функцию проверки. Обычно она устанавливается сразу после получения провайдера:

```ts
Provider.setPkgCheck((buffer: Buffer) => {
  // Пример: пакет должен быть длиной 8 байт, второй байт — 0x10
  if (buffer.length < 5) return false;
  return buffer.readUInt8(1) === 0x10 && buffer.length === 8;
});
```

Функция должна возвращать:
- `true` — если буфер содержит **полный** пакет (с точки зрения протокола);  
- `false` — если ожидается ещё часть данных.

❗ **Критически важно:** в этой функции **не следует** выполнять сложные проверки (например, CRC). Её задача — быстро определить, завершён ли пакет по формальным признакам (длина, заголовок и т.п.).

### Выполнение запроса

После установки функции `setPkgCheck` можно выполнять запрос:

```js
await this.Provider.request(buffer, timeout)
```

Параметры:
- `buffer` — `Buffer`, содержащий байты запроса;  
- `timeout` — время ожидания ответа в миллисекундах.

В случае ошибки будет выброшено одно из следующих исключений:

| Исключение                        | Описание |
|----------------------------------|----------|
| `V2NET_PROVIDER_REQ_TIMEOUT`     | Превышено время ожидания ответа. |
| `V2NET_PROVIDER_BUSY`            | Другой запрос уже выполняется (логическая ошибка в схеме). |
| `V2NET_PROVIDER_NOT_CONN`        | Нет соединения с преобразователем. |
| `V2NET_PROVIDER_SOCKET_ERROR`    | Ошибка записи в сокет. |
| `V2NET_PROVIDER_DESTROYED`       | Сокет был уничтожен во время запроса. |
| `V2NET_PROVIDER_SOCKET_TIMEOUT`  | Таймаут на уровне сокета. |
| `V2NET_PROVIDER_CANT_REQUEST`    | Провайдер временно не может выполнить запрос (например, ожидает срочное устройство). |
| `V2NET_PROVIDER_REQUIRE_BUS`     | Провайдер требует возврата управления в `ConverterBus` (например, при переключении контекста). |

Если запрос выполнен успешно — буфер с ответом можно получить через метод `getBuffer()`.

Пример работы с гипотетическим протоколом:

```ts
// Проверяем, можем ли выполнить запрос
this.Provider.canRequest();

// Устанавливаем функцию проверки пакета
this.Provider.setPkgCheck(data => data.length === 7);

// Формируем буфер запроса
const reqBuffer = this.makeSpecialRequest(1, 0x01, 0x01);

// Выполняем запрос (❗ обязательно с await!)
await this.Provider.request(reqBuffer, this.options.timeout);

// Анализируем ответ
const result = this.parseSpecialRequest(this.Provider.getBuffer());

// Обрабатываем результат: преобразуем в значения, обновляем выходы, shared-данные и т.п.
```

#### Краткое описание методов класса `TCPProvider`

- `setPkgCheck(callback: (buffer: Buffer) => boolean)`  
  Устанавливает функцию для определения завершённости входящего пакета.

- `request(buffer: Buffer, timeout: number): Promise<boolean>`  
  Выполняет одиночный запрос и ожидает полного ответа.

- `autoRequest(buffer: Buffer, timeout: number, maxRetries?: number): Promise<boolean>`  
  Выполняет запрос с автоматическими повторными попытками при таймауте.

- `getBuffer(): Buffer`  
  Возвращает буфер с полученными данными (только после успешного `request`).

- `addUrgentQueue(device: string)`  
  Добавляет устройство в срочную очередь на получение провайдера.

- `canRequest(): boolean`  
  Проверяет, может ли текущее устройство выполнить запрос (учитывает состояние соединения и срочную очередь). При невозможности выбрасывает исключение.

### Срочная очередь

Иногда устройству требуется **немедленно** выполнить запрос — например, чтобы обработать команду в реальном времени (включение реле, сброс состояния и т.п.).

Для этого можно поместить устройство в **срочную очередь**:

```ts
actionSetDO(data: { port: number, value: number }) {
  // Сохраняем команду на запись
  this.shares.writeDO.push(data);

  // Ставим себя в срочную очередь
  this.Provider.addUrgentQueue(this.id);
}
```

После этого, как только любое другое устройство вызовет `this.Provider.canRequest()`, будет выброшено исключение — потому что в срочной очереди находится другое устройство.

**ConverterBus** автоматически определит, к какому порту (`devX`) подключено это срочное устройство, и немедленно передаст ему управление.
